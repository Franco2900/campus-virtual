## D-039 — UI y modelo del chatbot (CU-11)

- Fecha: 2026-10-17.
- Decisión: el chatbot vive en una **página dedicada `/chat`** (feature `src/features/chatbot/` enlazada desde el sidebar, mismo patrón que los CUs anteriores) y usa el modelo **`qwen3:4b` vía Ollama local** (`langchain-ollama`), como prueba con un modelo liviano; si el comportamiento resulta insuficiente se evaluará escalar a uno más potente (p. ej. `qwen3:8b`).
- Contexto / problema: el CU-11 define el comportamiento funcional pero no la forma de la UI ni el modelo; ambas son decisiones de producto dependientes del hardware del usuario.
- Alternativas consideradas: UI — (a) panel lateral persistente (más pro, toca el shell global y complica la evidencia Playwright); (b) widget flotante global (máxima visibilidad, mayor complejidad e interferencia con capturas). Modelo — llama3.2:3b (más liviano), qwen2.5:3b, mistral:7b, qwen2.5:7b, qwen3:8b (primero elegido, luego reducido a 4b para la prueba).
- Criterios: la página `/chat` reutiliza el patrón de features y el pipeline de evidencia existente sin tocar el shell; `qwen3:4b` prioriza velocidad y bajo consumo de RAM en la etapa de prueba, dejando el escalado como evolución posterior.
- Consecuencias / impacto: la implementación sigue el patrón routes → services → models con un blueprint `chat` nuevo; el README deberá documentar `ollama pull qwen3:4b` como requisito de uso; cambiar el modelo en el futuro es una sola variable de configuración.
- Estado: Vigente.

## D-040 — Implementación del chatbot: agente, tools de solo lectura y fallo de Ollama

- Fecha: 2026-10-17.
- Decisión: el chatbot se implementa como **agente LangChain** en `backend/services/chat_service.py` con **herramientas de solo lectura** construidas por `build_tools` y scopeadas a la sesión del usuario: la identidad y los permisos SIEMPRE se resuelven desde la sesión de Flask (parámetro inyectado en cada tool), nunca desde el modelo. El blueprint `backend/blueprints/chat.py` expone `POST /api/chat/messages` (201 con el turno completo `user_message` + `assistant_message`; 400 contenido vacío; 401 sin sesión; **502** con mensaje amable si Ollama falla) y `GET /api/chat/messages` (historial persistido en `conversation`/`message`, migración `0008`). El historial se recorta a una **ventana de 10 mensajes** por turno como contexto del modelo; la base conserva el historial completo por usuario. Cuando el LLM falla el turno **no se persiste** (ni el mensaje del usuario ni la respuesta). Configuración por env (con defaults de desarrollo, D-J): `OLLAMA_MODEL` (default `qwen3:4b`), `OLLAMA_BASE_URL` (default `http://127.0.0.1:11434`), `OLLAMA_TIMEOUT` (default `120` s), `CHAT_HISTORY_WINDOW` (default `10` mensajes) y `CHAT_MESSAGE_MAX_LENGTH` (default `4000`). No se fija tope de tokens de salida (OQ-3 quedó deferido; si las respuestas resultan largas se puede agregar `num_predict` a `ChatOllama`).
- Contexto / problema: D-039 definió UI y modelo; faltaba decidir el diseño del servicio — integración LangChain, cómo scopingar permisos por rol sin confiar en el modelo, la política de persistencia del historial y el comportamiento ante fallo del LLM local (requisito A7 del spec).
- Alternativas consideradas: (a) tools con permisos resueltos por el propio modelo (descartada: viola la regla 16 del spec — el modelo nunca debe decidir permisos); (b) prompt-only sin tools (descartada: no entrega datos reales del sistema, que es el objetivo del CU); (c) streaming de tokens (descartado para la primera versión por complejidad en el proxy y la evidencia; queda como evolución).
- Criterios: las 6 tools delegan siempre en `services/` existentes (una sola fuente de verdad de negocio), el scope por rol se calcula en Python con la sesión de Flask, y una falla del modelo no corrompe el historial (turno atómico).
- Consecuencias / impacto: backend requiere `langchain` y `langchain-ollama` (ya en `requirements.txt`); la respuesta 502 se distingue del 201 por contract y la UI la muestra con alerta + toast + «Reintentar»; agregar una tool nueva = una función en `build_tools` que delegue en un service, sin tocar el blueprint.
- Estado: Vigente.

## D-043 — Borrado explícito del historial propio del chatbot (CU-11 ampliado)

- Fecha: 2026-10-19.
- Decisión: la eliminación del historial propio se implementa como **borrado explícito ordenado en el servicio** (`delete_history(user)` en `backend/services/chat_service.py`: mensajes → conversación en una sola transacción, sin cascade ORM y sin migración), expuesto como `DELETE /api/chat/messages` **idempotente** (200 con `{"message": "Historial eliminado"}` incluso sin historial; 401 sin sesión; roles Estudiante/Profesor/Administrador). La UI ofrece la opción "Eliminar historial" en `/chat` con **confirmación mediante `ConfirmDialog` de intención danger** y aviso de irreversibilidad; al confirmar, estado vacío y toast; al cancelar, no se borra nada. El **prompt del sistema** orienta al usuario hacia la opción de la interfaz y aclara que el modelo no ejecuta el borrado.
- Contexto / problema: ampliación del CU-11 (A9/A9.1 + reglas 14/16/17): el usuario debe poder eliminar completamente su historial propio. Borrar solo la conversación dejaría mensajes huérfanos, y el esquema no tenía ninguna mecánica de borrado.
- Alternativas consideradas: cascade a nivel ORM (`cascade`/`ondelete` en la relación `Conversation`→`Message`) — descartada porque exigía tocar los modelos y generar una migración sin cambio real de esquema, para un único punto de borrado que ya controla el servicio.
- Criterios: cero mensajes huérfanos sin tocar el esquema; identidad y permiso de borrado validados siempre en el backend desde la sesión (regla 16); el borrado solo alcanza al usuario propio y no toca datos funcionales como cursos, tareas, entregas, inscripciones ni calificaciones (regla 14); operación idempotente.
- Consecuencias / impacto: el servicio y el endpoint son la única vía de borrado; el historial eliminado no se recupera desde la aplicación ni vuelve al contexto del chatbot (regla 17); no hay migración ni cambio en los modelos; los tests cubren borrado completo, aislamiento, idempotencia, 401 y contexto vacío en el turno siguiente.
- Estado: Vigente.
