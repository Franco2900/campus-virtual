## Arquitectura y convenciones

- Capas respetadas: `blueprints/enrollments.py` y `blueprints/courses.py` solo serializan y mapean errores; las validaciones y reglas de negocio viven en `services/enrollment_service.py` y `services/course_service.py`; `models/enrollment.py` solo define campos. Sin SQL crudo en rutas.
- Autorización por rol con `@login_required` + `@require_roles(...)`, consistente con CU-02/CU-03/CU-04 y D-011/D-021.
- Esquema versionado con Flask-Migrate/Alembic (D-023): migración `0004_add_enrollment` (`down_revision=0003`); `flask db current` → `0004 (head)`; test de paridad modelos↔migraciones (`test_migrations.py`) sin diferencias.
- Duplicado a nivel de base: `UNIQUE(course_id, student_id)` (`uq_enrollment`) más el chequeo en servicio; el `IntegrityError` se traduce a `409` (defensa en profundidad).
- Frontend sobre el design system (D-019): `EnrollmentsPage` reutiliza `src/ui/` (`DataTable`, `Badge`, `ConfirmDialog`, `EmptyState`, etc.); sin colores hardcodeados; `data-testid` por elemento; errores del backend renderizados con `role="alert"`. `DataTable` se extendió con `testId`/`rowTestId` de forma retrocompatible; `ProtectedRoute` acepta `roles` (array) además de `role`.
- Decisiones registradas: D-024 (modelo `Enrollment` + semántica alta/activa-inactiva/baja física) y D-025 (`GET /api/courses/mine`).
- Mensajes de error de la API en español; el cliente solo envía y muestra.
- Docs sincronizadas: tabla API en `AGENTS.md` (5 endpoints CU-05), `README.md`, `decisiones.md` (D-024/D-025), `progreso.md`.
